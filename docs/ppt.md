> 用途：依本檔逐頁製作投影片。每頁含「標題 / 建議畫面 / 講稿要點 / 講者備註」。  
> 建議總頁數：12～15 頁（含封面與 Q&A）。風格偏學術實驗報告，避免過多裝飾。

## 頁 0｜封面

**標題**  
夜間 HDR 前處理模組：16-bit CLAHE 與 Real-time GPU Pipeline

**副標**  
提升 YOLO26 夜間偵測精度，並以記憶體預配置達成穩定即時處理

**建議畫面**  
- 左側：夜間原始 HDR / LDR 示意圖（暗）  
- 右側：CLAHE 增強後結果（亮、細節可見）  
- 底部：專案名 raw-clahe、日期

**講稿要點（30 秒）**  
我們用一層前處理，把夜間 16-bit HDR 增強成適合偵測的 LDR；同時把整個 GPU 流程壓到穩定毫秒級。

---

## 頁 1｜研究動機

**標題**  
夜間感知為什麼難？

**建議畫面**  
三欄痛點卡片（勿用太多 icon）：
1. 暗部動態範圍不足、雜訊大  
2. 模型多在日間 LDR 訓練  
3. 只靠重訓成本高、週期長

**講稿要點**  
夜間不是單純「調亮」；資訊藏在 16-bit 低碼值區。若先壓成 8-bit 再增強，細節可能已經沒了。

**講者備註**  
可問聽眾：你們覺得瓶頸在模型還是在輸入？

---

## 頁 2｜研究目標演化

**標題**  
從「免訓練」到「可部署的增強管線」

**建議畫面**  
時間軸 / 兩階段對比：

| 階段 | 目標 |
|------|------|
| 初始 | 單一前處理 → 後端模型**不必訓練**也能夜間感知 |
| 現況 | 16-bit CLAHE → LDR；證明 mAP 大幅提升 + GPU real-time；目前最強結果為 **enhance + fine-tune** |

**講稿要點**  
初衷很理想；實測後我們先把「輸入品質」與「即時性」做穩，再搭配 fine-tune 驗證端到端價值。免訓練路徑仍是下一步消融重點。

**講者備註**  
這頁要誠實：主結果不是 zero-shot，避免被問倒。

---

## 頁 3｜方法總覽（Pipeline）

**標題**  
方法：在 16-bit Domain 增強，再壓成 LDR

**建議畫面**  
橫向流程圖（一條線即可）：

`未白平衡 16-bit HDR → H2D →（灰世界白平衡）→ YUV CLAHE → Linear TM → LDR → YOLO26`

**講稿要點（1 分鐘）**  
關鍵只有一句：CLAHE 做在高動態域，Tone Mapping 只是最後出口。Y 通道增強、色度不動，避免色偏亂飛。

---

## 頁 4｜為什麼是 16-bit CLAHE？

**標題**  
先增強再量化，而不是先量化再增強

**建議畫面**  
左右對照表：

| 路徑 A（常見） | 路徑 B（本方法） |
|----------------|------------------|
| HDR → 8-bit → CLAHE | HDR → CLAHE → 8-bit LDR |
| 暗部可能已量化損失 | 暗部對比先拉開 |

可加一張「同一場景 before / after」對比圖（用 `result/enhanced`）。

**講稿要點**  
夜間有效資訊擠在低碼值；在 float/uint16 域做局部直方圖均衡，比在 8-bit 上硬拉對比更合理。

## 頁 5｜系統實作架構

**標題**  
模組分工

**建議畫面**  
簡潔架構圖：

```
main.py ──► loader.py (讀取 / H2D / WB)
       ├──► clahe.py  (GPU CLAHE workspace)
       ├──► tm.py     (Linear tone mapping)

```

**講稿要點**  
實驗程式刻意拆成「資料搬運 / 增強 / 映射 / 量測」，方便之後加開關（例如雙邊濾波）與消融。

## 頁 6｜GPU 優化核心（重點頁）

**標題**  
不靠多執行緒：靠「預挖記憶體格子」與同步策略

**建議畫面**  
四個短要點（大字）：

1. **Workspace 預配置**：迴圈內零動態配置  
2. **Pinned Memory**：批次 H2D / D2H  
3. **Chunk 級 sync**：避免逐張 synchronize → 降頻  
4. **延後寫檔**：GPU 跑完再寫 PNG  

可附一張「優化前延遲尖峰 vs 優化後平坦」示意（用 latency chart）。

**講稿要點（1.5 分鐘）**  
傳統 CLAHE 理論上延遲該很穩；我們早期不穩，是因為 allocator 碎片與 GPU 降頻，不是演算法本身。把同步拿掉、格子先挖好，P99 就能壓到約 2.4 ms。

**講者備註**  
這頁是工程貢獻的核心，多留時間。

**標題**  
前處理達到 Real-time，且穩定

**建議畫面**  
大數字三個：

- **P99 ≈ 2.39 ms**  
- **0 / 2230** 超過 30 ms  
- 解析度 **800×1200**，張數 **2230**

**講稿要點**

## 頁 9｜主結果：mAP 大幅提升（最重要結果頁）

**標題**  
夜間偵測：從幾乎失效 → 可用

**建議畫面**  
完整對照表（與實驗圖一致）：

**Baseline（w/o enhance & fine-tune）**
- mAP50 ≈ 0.0008～0.002  
- mAP50-95 ≈ 0.0004～0.0007  
- Inf.：n 2.5 / s 3.7 / m 5.5 / l 6.7 / xl 10.9 ms  

**Ours（w enhance & fine-tune）**
- mAP50：**0.672～0.757**（n→xl）  
- mAP50-95：**0.441～0.533**  
- Inf.：n 1.7 / s 2.1 / m 3.2 / l 3.8 / xl 6.4 ms  

可用長條圖強調 mAP50 數量級差異（0.001 vs 0.7）。

**講稿要點（1 分鐘）**  
沒有增強時模型幾乎看不到東西；增強後再 fine-tune，mAP50 直接進入 0.67 以上。這證明輸入域處理對夜間任務不是可有可無。

---

## 頁 10｜速度結果：增強沒有拖慢端到端

**標題**  
Inference Time：實驗組反而更快

**建議畫面**  
折線或分組柱狀圖：Baseline vs Ours 的 Inf. Time（n→xl）。  
標註：xl **10.9 → 6.4 ms**。

**講稿要點**  
大家直覺會怕「多一段前處理會變慢」。我們的數據顯示：前處理本身很輕，且增強後的輸入可能讓偵測路徑更穩定，整體推論時間不升反降。

**講者備註**  
若被問因果：誠實說可能與輸入分佈、後處理、實作細節有關，需進一步 profiling。

我們證明了什麼？還沒證明什麼？

**講稿要點**

## 頁 13｜結論

**標題**  
結論

**建議畫面**  
三句話大字（建議逐條出現）：

1. 在 **16-bit domain** 做 CLAHE，再映射到 LDR，是有效的夜間輸入策略。  
2. 透過 **GPU workspace 預配置與 chunk 級同步**，傳統增強可達 **P99 ≈ 2.39 ms** 的穩定即時。  
3. 搭配 YOLO26 fine-tune，夜間 **mAP50 從 ≈0 提升至 0.67～0.76**，且推論時間未惡化。

**講稿要點（20 秒）**
